First 10 minutes: learner quickstart

The fastest way to understand CodeUp is to complete this short loop once. The detailed learner guide begins immediately after it.

  1. Open CodeUp IDE and let the workspace finish loading.
  2. Move to the Code editor and enter this program: 
    name = "Learner"
print("Hello", name)
  3. Press Ctrl+Enter. Read or listen to Program output and confirm that the program prints “Hello Learner”.
  4. Change the value of name, run the program again, and confirm that the output changes with the code.
  5. Move to the command box and type “give me a code map”. Use the response to identify the structure of the short program.
  6. Type “explain this code”. Compare the explanation with what you think each line does.

You have completed CodeUp’s core learning loop: edit code → run → inspect output → change code → inspect structure → ask for an explanation. The rest of Part I expands each step.

Part I. Learner Guide

1. What CodeUp is

CodeUp is a browser-based, blind-first Python learning environment for beginners. A learner can type Python, run it, hear or read the output, understand errors, inspect program structure, follow values while code executes, work through lessons and guided projects, and participate in an instructor-managed classroom. The current build supports typed commands, keyboard workflows, optional microphone voice commands, Screen Reader Safe or CodeUp Voice narration, cursor-aware indentation explanations, fast structural overviews, exact code reading, context resume, semantic search, and output-orientation commands for nonvisual programming. CodeUp is designed for the early stage of learning Python, where concepts such as variables, indentation, loops, conditions, functions, program state, and errors still need to be understood. It can later serve as a bridge toward general development tools such as VS Code.

IMPORTANT Voice is optional. The complete learning workflow is available through the keyboard and screen-reader navigation. On a first visit, CodeUp defaults to Screen Reader Safe so an active screen reader remains the primary voice. Learners can switch to CodeUp Voice if they want CodeUp to narrate automatically. Microphone-based voice commands remain optional.

5. Accessibility and display settings

5.1 Assistive-technology profile

Settings includes an assistive-technology profile. Choices include Default, NVDA, JAWS, Windows Narrator, VoiceOver, Orca, and a VS Code handoff-oriented profile. The profile helps CodeUp choose appropriate interaction and speech behavior. Choose the profile that matches the screen reader you actually use.

5.2 Speech mode: Screen Reader Safe

Screen Reader Safe is the default speech mode for a first visit. CodeUp stays quiet automatically so the learner’s screen reader is the primary voice, while status updates are exposed through accessible ARIA regions. Explicit requests such as read output again or explain error can still speak because the learner asked for that narration. CodeUp supports the screen reader; it does not replace it.

5.3 Speech mode: CodeUp Voice

CodeUp Voice makes CodeUp the automatic narration channel. When this mode is active, CodeUp suppresses duplicate live-region announcements for content it is already speaking so CodeUp Voice and an active screen reader do not announce the same event at once. Use this mode when the learner wants CodeUp to narrate program output, guidance, and responses automatically.

5.4 Speech rate and voice

When CodeUp Voice is used, the speech settings provide a rate control from approximately 0.5x to 2x, a browser voice selector, and a Test Voice action. Choose a rate that is comfortable for learning. Faster speech is useful only when comprehension remains high.

7. Writing Python manually

  1. Move to the Code editor.
  2. Type Python exactly as you would in a normal code editor.
  3. Use indentation carefully. Python uses indentation as part of its syntax.
  4. Run with Ctrl+Enter or the Run control.
  5. Read the Program output area after the run.
  6. If an error occurs, CodeUp exposes the error and its debugging tools instead of hiding the failure.
name = input("What is your name? ")
print("Hello", name)

For beginners, instructors should encourage manual typing for core exercises. Code generation can be useful for demonstrations or exploration, while manual typing provides stronger practice with syntax and structure.

8. Running a program and reading output

Run executes the current Python program inside CodeUp’s sandboxed runtime. Printed output is shown in Program output. Runtime errors are available to the error-analysis and narration features. Output replay lets a learner hear long output again without rerunning the program just to hear it a second time.

CLASSROOM TIP

For an exercise, ask learners to predict the output before pressing Run. This turns the run button into a comprehension check rather than a trial-and-error button.

8.1 Long output orientation

When a program prints many lines, orient yourself before replaying the whole output. These commands use the stored result of the most recent run, so you can quickly learn its size and endpoints without rerunning the program.

how many lines of output
first line of output
last line of output

Use read output or read last output when you want the complete stored output. Output orientation also handles output that contains blank lines rather than treating it as if the program never ran.

9. Python input() and program inputs

Programs that call input() need learner-supplied values. CodeUp supports both prepared input values and live input interactions.

9.1 Prepared input values

The Program inputs area can hold values before a run. The canonical command is use followed directly by the value. For example, use Alexis or use 16. Do not add “as input” to the command. If a program asks for more than one value, provide each value in prompt order.

read input prompt
use Alexis
use 16
read input values
clear input values
cancel input

INPUT COMMAND RULE: Type or say use followed directly by the value. Examples: use Alexis; use 16. Do not use “use 16 as input” in this guide.

9.2 Live input

Live input is useful when the program should ask for each value as it reaches input(). When CodeUp asks for a value, use the same short form: use Alexis, use 16, or use another value. For multiple prompts, answer one prompt at a time. Classroom commands such as Join ABC123 still route as classroom actions rather than program input.

10. The command box

The command box accepts natural-language instructions. Typed commands are the most reliable baseline because they do not depend on microphone permission or speech-recognition quality. Many important commands are deterministic and do not need an AI model.

10.1 A good beginner pattern

  1. Write or open some code.
  2. Type one short command.
  3. Listen to or read CodeUp’s response.
  4. Check the editor/output to confirm what changed.
  5. Use a follow-up command only after the first action is understood.

11. Optional voice commands

Voice commands use the browser microphone and speech-recognition controls. The command meaning is the same as typing the phrase into the command box. Voice recognition is optional and separate from speech mode: the microphone controls whether CodeUp listens, while Screen Reader Safe versus CodeUp Voice controls how responses are narrated.

start live assistant
pause listening
stop speaking

Ctrl+Shift+M toggles microphone voice control from the keyboard. The same deterministic command set remains available through typing if microphone recognition is unavailable or inconvenient.

Learners can switch between voice and the command box at any time, so the same workflow remains available through typing.

16. Variables and program state

State tools help a learner answer “what values exist right now?” instead of mentally simulating every line.

Variable/state views are most useful after a run or during a debugging walkthrough. In classroom assignments, instructors can allow or disable Variable Watch independently from other AI assistance.

17. Step Narration

Step Narration walks through execution in smaller steps and explains what the program is doing. It is useful for loops, changing variables, branch decisions and function calls.

step through this

A productive classroom pattern is to pause after each meaningful step and ask the learner what will happen next.

18. Errors and debugging

When Python fails, CodeUp surfaces the runtime error and supports several ways to investigate it.

explain error
where did it crash
what caused this
what value caused this
fix with explanation
read last error

18.1 Recommended learner debugging sequence

  1. Run the program and listen to/read the actual error first.
  2. Ask where the program crashed.
  3. Ask what caused the error or what value was involved.
  4. Try to predict the repair before asking CodeUp to fix anything.
  5. If using “fix with explanation,” review the proposed change and understand the reason.
  6. Run again and confirm the behavior rather than assuming the edit solved the problem.

19. Error Trace Narration and Mistake Replay

The runtime and accessibility layers keep structured information about recent failures. Error Trace Narration can explain the important location/cause information around a crash. Mistake or error replay lets the learner revisit a recent failure and its correction rather than losing the teaching moment after the code changes.

20. Conditional breakpoints and focused debugging

CodeUp supports beginner-friendly debugging concepts, including breakpoints that can be associated with conditions such as a value crossing a threshold. These tools are intended to help a learner hear when a meaningful state is reached, rather than forcing continuous inspection of every line.

Example condition: total > 10

Use conditional breakpoints only after the learner understands the variable being watched and the condition being tested.

21. Indentation and structural cues

Python indentation is meaningful. CodeUp now provides cursor-aware, deterministic explanations of indentation and enclosing blocks so a blind learner does not have to infer hierarchy from spaces alone. These tools complement the Audio Code Map, Step Narration, sonification, and Audio Blocks views.

21.1 Why a line is indented

These commands explain the current cursor line using the actual Python block structure. They report enclosing loops, conditions, functions, and the current indentation depth instead of only reading leading spaces.

how deep am I
what is inside this loop

If indentation is temporarily malformed, CodeUp can still explain the indentation problem rather than forcing the learner to repair it visually first.

21.2 Fast overview and structural navigation

Use overview for a quick semantic skim of the program. It reports the line count, named functions when present, and a useful structural landmark. Relative block navigation lets the learner move through the hierarchy without repeatedly searching for line numbers, and CodeUp speaks a short orientation cue after supported navigation jumps.

Mental Map combines the useful context CodeUp already knows - current code location, recent execution/state information, a recent error, and the last recorded change when available - into a short orientation response. Unified execution questions combine trace and condition facts so the learner can ask one question instead of opening several tools.

21.6 Precision Mode

Precision Mode is for exact proofreading on demand. Normal narration avoids reading every symbol because that becomes exhausting; Precision Mode can instead preserve case, punctuation, and character-level detail when a short line is difficult to verify nonvisually.

Textual program flow gives a conservative linear explanation of what the program does and points the learner back to Code Map or Step Narration when control flow becomes too complex to summarize safely. Braille Compact View is experimental: it compresses leading indentation into short depth markers such as D0, D1, or D3 so repeated spaces do not consume unnecessary Braille cells.

Semantic find labels why each whole-word occurrence appears in the program - for example an assignment, condition, function call, return, string, or comment - instead of returning bare line numbers. If the file has a temporary syntax error during editing, CodeUp falls back to a conservative lexical scan rather than claiming the name is missing. For two similar identifiers, compare reads the exact character difference.

Learners should distinguish between asking for an explanation and asking the system to perform the task. The former can support understanding while still leaving the learner responsible for the code.

Part III. Running a Class or Program

69. Recommended first-cohort setup

For a first program rollout, start with a cohort size the instructor can comfortably support. Use one clear lead instructor or coordinator and a short sequence of beginner Python sessions. Scale according to staffing, devices, and learner support needs. The goal is a repeatable routine: join, learn, run, debug, ask for help, submit, and review progress.

Implementation elementRecommended starting point
LearnersA manageable first cohort based on available staff, devices, and learner support needs.
Instructor/coordinatorOne named person who owns the cohort and consolidates feedback.
SessionsA short sequence of beginner sessions, paced to learner progress.
DevicesEach learner has a laptop/desktop, browser, internet and usual assistive technology.
Teaching levelComplete beginners are acceptable.
Primary goalConfirm learners can independently enter, run, understand and debug beginner Python while the instructor can manage the class.

70. Suggested Session 1: Orientation, output and variables

  1. Open CodeUp and complete the short interface orientation/tutorial.
  2. Confirm that keyboard and screen-reader navigation work comfortably for each learner.
  3. Write and run print("Hello").
  4. Introduce variables and print variable values.
  5. Demonstrate the command box with “what can I do here” and one explanation command.
  6. Show how CodeUp reads an error by deliberately introducing one small syntax or name error.
  7. End with a two-variable mini exercise and collect immediate accessibility feedback.

71. Suggested Session 2: Input, conditions and debugging

  1. Review variables.
  2. Introduce input() and CodeUp program-input handling.
  3. Write a simple age, marks, or name program.
  4. Introduce if/else.
  5. Use the error trace or explanation tools after a deliberate mistake.
  6. Show Audio Code Map or Step Narration on a short conditional program.
  7. Have learners ask for instructor help through the classroom system once so the workflow is familiar before they truly need it.

72. Suggested Session 3: Assignment and guided project

  1. Instructor publishes a short assignment.
  2. Learners open it from the classroom and write code manually.
  3. Learners run, correct mistakes and submit.
  4. Instructor reviews incoming submissions and help requests and inspects one submission.
  5. Open the Student Marks guided project or an instructor-created project.
  6. Finish with learner feedback about navigation, speech, errors, instructions, and instructor support.

75. Data and privacy

Classroom records include instructor accounts, cohorts, learner display names, learner tokens, assignments, code and progress, help requests, curriculum progress, guided-project progress, concept progress, and activity events. Instructor exports can contain learner progress. Treat these as classroom records.

  • Use learner display names that fit your organization’s privacy policy. The learning workflow does not require full legal names.
  • Do not share instructor passwords.
  • Keep cohort join codes within the intended learner group.
  • Do not put secrets, passwords, or sensitive personal data inside programming exercises or submitted code.
  • Store downloaded reports and CSV files only where your organization normally stores learner records.

76. Accessibility feedback and support

Instructors and coordinators can use learner feedback to refine classroom routines for different screen-reader, browser, keyboard, and speech preferences. The most useful feedback describes the exact action, what the learner heard or experienced, and what would have made the step clearer.

When reporting an accessibility issue, include the screen reader or other assistive technology, browser, exact action, what was announced or displayed, and what the learner expected. This makes support and follow-up faster.

77. Screen Reader Safe versus CodeUp Voice

CodeUp now exposes two speech modes instead of separate speech toggles. Screen Reader Safe keeps automatic CodeUp narration quiet so the learner’s screen reader is the primary voice. CodeUp Voice makes CodeUp narrate automatically and suppresses duplicate live-region announcements for content it is already speaking. If a learner reports overlapping speech, first confirm the selected speech mode in Accessibility and speech settings.

78. AI settings and classroom continuity

AI assistance is optional and instructor-controlled. Core classroom controls, deterministic command routing, curriculum checks, guided-project checkpoints, Python execution, keyboard navigation, and accessibility structure operate independently from optional AI assistance.

85. Learner quick-reference checklist

  • Open the CodeUp IDE and confirm the editor and Program output are reachable.
  • Use keyboard first; voice is optional.
  • Select the correct screen reader profile if applicable.
  • Write code manually for instructor exercises unless the assignment policy says otherwise.
  • Run with Ctrl+Enter or Run.
  • Read the error before asking for a fix.
  • Use code map, state watch, or Step Narration when they help you understand the program.
  • In a classroom, open the assignment before submitting.
  • Use “I need help” when instructor assistance is required.
  • Use Back to CodeUp after submitting to continue in the normal IDE.

  • Sign in with your own instructor account.
  • Create one cohort per learner group and share its join code.
  • Create assignments as drafts, review them, then publish.
  • Choose AI permissions intentionally. Accessibility fundamentals remain available.
  • Keep the cohort dashboard open during a live class for learner/help/submission updates.
  • Use Help queue to acknowledge requests.
  • Inspect submissions and learner detail when intervention is needed.
  • Use custom lessons/projects only when they add teaching value.
  • Handle exported reports and CSV files carefully because they contain learner records.
  • Confirm the instructor account, cohort, learner join flow, sample assignment, help queue, and submission flow before the first session.

101. Deterministic features versus optional AI

Mostly deterministic / local logicOptional AI-assisted
Python execution and outputOpen-ended code generation
Classroom join/navigation/submission/help commandsSome natural-language explanations
Instructor cohort/assignment recordsSome fix/explanation/tutor responses
Curriculum attempt/challenge checksOpen-ended concept tutoring where configured
Guided-project checkpointsGrounded AI assistance where a provider is configured
Code/project structure parsingAI may explain parsed structure in natural language when enabled.
Many editing/navigation commandsAI may assist with open-ended editing requests when enabled.
Accessibility semantics and keyboard navigationNo AI required.

This separation lets instructors choose AI assistance according to the learning goal while keeping the core classroom workflow consistent.
